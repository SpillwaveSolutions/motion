## 3. Context and problem statement

### 3.1 Problem description

The ImageGen block creates a PNG. Motion must store the image so that the note shows it after save and reload, in both modes. A file path from the temp folder of one machine would break on another machine.

**Problem statement as a question**: Where does Motion store a generated image?

### 3.2 Why this decision is needed

- **Business context**: BR-002 needs images to stay with the note.
- **Technical context**: FR-020 (generate an image from a prompt). NFR-I-003 (data portability).
- **Regulatory context**: None. Motion is not a regulated service.

### 3.3 Supporting links

- **Requirements**: BR-002, FR-020, NFR-I-003
- **Design doc**: section 6.10
- **Related ADRs**: None

## 5. Considered options

The options come from the design doc and from the code history. This record does not invent alternatives that nobody considered.

### Option 1: Inline `data:image/png;base64` URI on the node (chosen)

**Description**: `generateImage()` in `src/lib/imageGen.ts` and `run_image_cli` in `src-tauri/src/lib.rs` return a data URI. The node stores it in `src`.

**Wardley evolution stage**: Custom

#### Good (pros)

- Mirrors how DiagramGen stores Mermaid text.
- No asset-protocol plumbing in Tauri.

#### Bad (cons)

- The file grows by about 1.3 times the PNG size.

#### Cost analysis

- **CAPEX**: Not recorded. Motion has no budget (ARC-001-REQ). The cost is maintainer and agent time.
- **Relative effort**: Low.

### Option 2: Files in a workspace `assets/` folder

**Description**: Write the PNG next to the note and link it.

**Wardley evolution stage**: Custom

#### Good (pros)

- Small Markdown files, diffable images.

#### Bad (cons)

- Needs asset-protocol work in Tauri and a write path through the jail.

#### Cost analysis

- **CAPEX**: Not recorded. Motion has no budget (ARC-001-REQ). The cost is maintainer and agent time.
- **Relative effort**: Medium.

### Option 3: Do nothing (baseline)

**Description**: Keep the state before this decision.

#### Good

- No new work.

#### Bad

- Images vanish on reload.

#### Cost analysis

- **CAPEX**: None.
- **Relative effort**: None now. The cost appears as defects later.

## 6. Decision outcome

### 6.1 Chosen option

**Inline `data:image/png;base64` URI on the node**

### 6.2 Y-statement

> In the context of a block that creates images in two runtimes,
> facing a portable store for the image,
> we decided for inline base64 data URIs on the node,
> to achieve notes that carry their own images,
> accepting larger Markdown files.

### 6.3 Justification

- The comment in `src/lib/imageGen.ts` records the rationale, the cost, and the upgrade path.

---

## 7. Consequences

### 7.1 Positive consequences

- A copied note shows its images with no extra files.

### 7.2 Negative consequences (accepted trade-offs)

- Larger files and noisy diffs.
- Export keeps only the alt text of an image. A themed PDF or Word file loses the picture (work item 01M5GQ20CANKH5P50X4QC523WM).

### 7.3 Neutral consequences

- The upgrade path is a workspace `assets/` folder.

### 7.4 Risks and mitigations

| Risk | Likelihood | Impact | Mitigation | Owner |
|------|------------|--------|------------|-------|
| Notes become too large to edit or diff | Medium | Low | Move to workspace asset files when this happens. | Rick Hightower |
