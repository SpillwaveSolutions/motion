## 3. Context and problem statement

### 3.1 Problem description

A Query block holds SQL that runs in DuckDB-WASM in the page. A note is untrusted input. Motion needs to stop a note from changing data or reading outside the registered tables.

**Problem statement as a question**: How does Motion limit the SQL that a document can run?

### 3.2 Why this decision is needed

- **Business context**: BR-002 (one tool from draft to delivery) includes queries over local data.
- **Technical context**: NFR-SEC-005 (treat note content as untrusted). FR-019 (run read-only SQL).
- **Regulatory context**: None. Motion is not a regulated service.

### 3.3 Supporting links

- **Requirements**: BR-002, FR-019, NFR-SEC-005
- **Design doc**: section 6.8
- **Related ADRs**: None

## 5. Considered options

The options come from the design doc and from the code history. This record does not invent alternatives that nobody considered.

### Option 1: Validation before execution (chosen)

**Description**: `validateSelectSql()` accepts one statement that starts with SELECT or WITH, and blocks 19 mutating verbs by word boundary. `validateIdentifier()` checks table names. `escapeSqlString()` escapes paths. `clampLimit()` caps results at 10,000 rows.

**Wardley evolution stage**: Custom

#### Good (pros)

- Small, testable functions.
- The blast radius is data that you already own.

#### Bad (cons)

- A keyword block list is weaker than a parser or a read-only connection.

#### Cost analysis

- **CAPEX**: Not recorded. Motion has no budget (ARC-001-REQ). The cost is maintainer and agent time.
- **Relative effort**: Low.

### Option 2: A SQL parser

**Description**: Parse the statement and allow only read nodes.

**Wardley evolution stage**: Custom

#### Good (pros)

- Strong guarantee.

#### Bad (cons)

- A new dependency and more code for an in-memory engine.

#### Cost analysis

- **CAPEX**: Not recorded. Motion has no budget (ARC-001-REQ). The cost is maintainer and agent time.
- **Relative effort**: Medium.

### Option 3: Do nothing (baseline)

**Description**: Keep the state before this decision.

#### Good

- No new work.

#### Bad

- A note could run DDL against the in-memory database.

#### Cost analysis

- **CAPEX**: None.
- **Relative effort**: None now. The cost appears as defects later.

## 6. Decision outcome

### 6.1 Chosen option

**Validation before execution**

### 6.2 Y-statement

> In the context of SQL from untrusted notes in an in-page engine,
> facing statements that change data,
> we decided for validation of statement shape, identifiers, and limits,
> to achieve read-only queries with capped results,
> accepting a block list as the weaker part.

### 6.3 Justification

- DuckDB runs in the page over files that you already can open. A bypass gives no new privilege.

---

## 7. Consequences

### 7.1 Positive consequences

- DDL and multi-statement SQL fail before they reach DuckDB.

### 7.2 Negative consequences (accepted trade-offs)

- A clever statement can pass the block list. Mitigation: the engine has no write access to the filesystem.

### 7.3 Neutral consequences

- Unit coverage sits in `src/lib/Integration.test.ts`, not in a `sqlSafety.test.ts` file.

### 7.4 Risks and mitigations

| Risk | Likelihood | Impact | Mitigation | Owner |
|------|------------|--------|------------|-------|
| DuckDB gains filesystem write access or `ATTACH` becomes reachable | Low | High | Move to a parser-level check at that point. | Rick Hightower |
