## 3. Context and problem statement

### 3.1 Problem description

The client renders documents, AI output, and imported content. Any of these can try to make the client send a bad request. The desktop command wrappers once held their own copy of the path rules, and the two runtimes drifted apart.

**Problem statement as a question**: Where do the security rules for file access live?

### 3.2 Why this decision is needed

- **Business context**: BR-001 needs the jail to hold in both modes.
- **Technical context**: NFR-SEC-001 to NFR-SEC-005.
- **Regulatory context**: None. Motion is not a regulated service.

### 3.3 Supporting links

- **Requirements**: BR-001, FR-009, FR-013, NFR-SEC-001, NFR-SEC-002, NFR-SEC-004
- **Design doc**: section 6.7
- **Related ADRs**: ADR-001, ADR-002, ADR-003

## 4. Decision drivers (forces)

### 4.1 Technical drivers

## 5. Considered options

The options come from the design doc and from the code history. This record does not invent alternatives that nobody considered.

### Option 1: Rules in the shared cores, thin wrappers (chosen)

**Description**: `src-tauri/src/lib.rs` commands and `src/server.ts` routes call `fs_core` and `fsCore`. They hold no path rules.

**Wardley evolution stage**: Custom

#### Good (pros)

- The contract tests every rule.
- One place to change a rule in each language.

#### Bad (cons)

- Wrappers must stay thin. Review must enforce it.

#### Cost analysis

- **CAPEX**: Not recorded. Motion has no budget (ARC-001-REQ). The cost is maintainer and agent time.
- **Relative effort**: Low.

### Option 2: Tauri filesystem plugin scopes

**Description**: Use the plugin's permission scopes as the jail.

**Wardley evolution stage**: Custom

#### Good (pros)

- Less custom code.

#### Bad (cons)

- Desktop only.
- Not the workspace mechanism and not contract-tested.

#### Cost analysis

- **CAPEX**: Not recorded. Motion has no budget (ARC-001-REQ). The cost is maintainer and agent time.
- **Relative effort**: Low.

### Option 3: Checks in the client

**Description**: Hide outside paths in the UI.

**Wardley evolution stage**: Custom

#### Good (pros)

- Simple.

#### Bad (cons)

- Protects nothing against a crafted request.

#### Cost analysis

- **CAPEX**: Not recorded. Motion has no budget (ARC-001-REQ). The cost is maintainer and agent time.
- **Relative effort**: Low.

### Option 4: Do nothing (baseline)

**Description**: Keep the state before this decision.

#### Good

- No new work.

#### Bad

- Wrappers keep their own rules, and the runtimes drift again.

#### Cost analysis

- **CAPEX**: None.
- **Relative effort**: None now. The cost appears as defects later.

## 6. Decision outcome

### 6.1 Chosen option

**Rules in the shared cores, thin wrappers**

### 6.2 Y-statement

> In the context of two backends that serve an untrusted client,
> facing rules that drift when they live in wrappers,
> we decided for all jail rules in the shared, contract-tested cores,
> to achieve one tested copy of each rule in each language,
> accepting discipline to keep wrappers thin.

### 6.3 Justification

- The `lib.rs` comment records that a second copy of the rules "is what let the two runtimes drift apart in the first place."

---

## 7. Consequences

### 7.1 Positive consequences

- Every path from the client is re-derived at the boundary.

### 7.2 Negative consequences (accepted trade-offs)

- The Tauri filesystem plugin is still registered. Its scopes are not the jail. Mitigation: no command uses the plugin for workspace files.

### 7.3 Neutral consequences

- Publish tokens are outside this decision. They live in webview storage (work item 01M5GQ20K7RQ0WTFF1973915BP).

### 7.4 Risks and mitigations

| Risk | Likelihood | Impact | Mitigation | Owner |
|------|------------|--------|------------|-------|
| A new command adds its own path logic | Low | High | P-3 gate: each command maps to a core function. | Rick Hightower |
