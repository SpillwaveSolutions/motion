## 3. Context and problem statement

### 3.1 Problem description

Motion runs in two modes. Browser mode stores files through a Bun process. Desktop mode stores files through a Rust process. The two processes cannot share code. Before this decision, the two storage implementations drifted apart in seven ways, and code review did not find the drift.

**Problem statement as a question**: How does Motion keep two storage implementations in two languages identical?

### 3.2 Why this decision is needed

- **Business context**: BR-001 (local-first editing) and BR-004 (a native macOS desktop product) need both modes to store files the same way.
- **Technical context**: NFR-SEC-002 (containment in both cores) and NFR-M-004 (verification gate). FR-001, FR-009, and FR-011 to FR-013 run through both cores.
- **Regulatory context**: None. Motion is not a regulated service.

## 5. Considered options

The options come from the design doc and from the code history. This record does not invent alternatives that nobody considered.

### Option 1: Hand-written, language-neutral contract that both suites run (chosen)

**Description**: A JSON fixture lists setup, operations, and expected result classes. The TypeScript and Rust test suites both load it.

**Wardley evolution stage**: Custom

#### Good (pros)

- A difference between the cores fails a build.
- Neither implementation is the reference. The fixture is.
- A case can record the incident that it pins in a `_why` field.

#### Bad (cons)

- Each storage change needs three edits: the fixture, TypeScript, and Rust.
- The fixture has no per-implementation opt-out.

#### Cost analysis

- **CAPEX**: Not recorded. Motion has no budget (ARC-001-REQ). The cost is maintainer and agent time.
- **Relative effort**: Medium.

### Option 2: Share one implementation through WebAssembly or a foreign function interface

**Description**: Compile one core and call it from both runtimes.

**Wardley evolution stage**: Custom

#### Good (pros)

- One copy of the logic.

#### Bad (cons)

- High build complexity for about 160 lines of logic.
- Puts a Rust toolchain in the browser-mode dependency path.

#### Cost analysis

- **CAPEX**: Not recorded. Motion has no budget (ARC-001-REQ). The cost is maintainer and agent time.
- **Relative effort**: High.

### Option 3: Generate the fixture from the TypeScript implementation

**Description**: Record the current TypeScript behavior and replay it against Rust.

**Wardley evolution stage**: Custom

#### Good (pros)

- No hand-written cases.

#### Bad (cons)

- TypeScript becomes the reference, including its bugs.
- The generator is a third artifact that can drift.

#### Cost analysis

- **CAPEX**: Not recorded. Motion has no budget (ARC-001-REQ). The cost is maintainer and agent time.
- **Relative effort**: Medium.

### Option 4: Do nothing (baseline)

**Description**: Keep the state before this decision.

#### Good

- No new work.

#### Bad

- The two cores keep drifting. Review did not stop the drift before (seven differences in `fsCore.ts` history).

#### Cost analysis

- **CAPEX**: None.
- **Relative effort**: None now. The cost appears as defects later.

## 6. Decision outcome

### 6.1 Chosen option

**Hand-written, language-neutral contract that both suites run**

### 6.2 Y-statement

> In the context of two storage implementations in two languages,
> facing drift that review does not find,
> we decided for a hand-written, language-neutral contract that both test suites run,
> to achieve a red build for any difference,
> accepting three edits for each storage change.

### 6.3 Justification

- The fixture is the only reference, so a bug in one language does not become the specification.
- Error cases assert a class (`ok`, `denied`, `not-found`, `not-a-directory`), so each language words its errors freely.

## 7. Consequences

### 7.1 Positive consequences

- Drift becomes a build failure. Baseline: 7 known drifts. Target: 0.
- Reviewers read one file to know what storage does.

### 7.2 Negative consequences (accepted trade-offs)

- Three edits for each new storage behavior. Mitigation: a new case fails at least one suite at once, so a missing edit cannot merge.

### 7.3 Neutral consequences

- Contributors learn the fixture format and the `$ROOT` and `$OUTSIDE` placeholders.

### 7.4 Risks and mitigations

| Risk | Likelihood | Impact | Mitigation | Owner |
|------|------------|--------|------------|-------|
| The fixture does not cover a new behavior | Medium | High | Each storage pull request adds a case (P-2 gate). | Rick Hightower |
| Settings have no such contract | High | Medium | Work item 01M5GQ207P956J179YGENY9ERT. Consider a settings fixture. | Rick Hightower |
