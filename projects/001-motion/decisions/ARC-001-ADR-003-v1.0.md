## 3. Context and problem statement

### 3.1 Problem description

The dev server reads and writes files for browser mode. If a request could set the workspace root, the jail would surround a folder that the caller picks. Any page or local process could then read any file that the dev server user can read.

**Problem statement as a question**: Where does each backend get the root of its workspace jail?

### 3.2 Why this decision is needed

- **Business context**: BR-001 needs the jail to protect the files of the writer.
- **Technical context**: NFR-SEC-001 (no accounts, localhost only) and NFR-SEC-002 (containment).
- **Regulatory context**: None. Motion is not a regulated service.

### 3.3 Supporting links

- **Requirements**: BR-001, BR-005, FR-001, NFR-SEC-001, NFR-SEC-002
- **Design doc**: section 6.3
- **Related ADRs**: ADR-007

## 5. Considered options

The options come from the design doc and from the code history. This record does not invent alternatives that nobody considered.

### Option 1: Read the root once from `MOTION_WORKSPACE`. Desktop sets it only through the folder dialog. (chosen)

**Description**: The dev server resolves `MOTION_WORKSPACE`, default `public/demo`, at startup. The native backend sets its root in `set_workspace` and holds it in `WorkspaceState`. `list_markdown_files` can no longer re-root it.

**Wardley evolution stage**: Custom

#### Good (pros)

- No request can widen the jail.
- E2E runs point the root at a seeded temp folder.

#### Bad (cons)

- Browser mode serves one workspace per server process.
- `HttpStorage.listFiles` ignores its `path` argument.

#### Cost analysis

- **CAPEX**: Not recorded. Motion has no budget (ARC-001-REQ). The cost is maintainer and agent time.
- **Relative effort**: Low.

### Option 2: Accept the root as a request parameter

**Description**: The client sends the folder with each call.

**Wardley evolution stage**: Custom

#### Good (pros)

- Multi-workspace browser mode.

#### Bad (cons)

- Turns the dev server into an arbitrary-file read API for anything that reaches the port.

#### Cost analysis

- **CAPEX**: Not recorded. Motion has no budget (ARC-001-REQ). The cost is maintainer and agent time.
- **Relative effort**: Low.

### Option 3: Do nothing (baseline)

**Description**: Keep the state before this decision.

#### Good

- No new work.

#### Bad

- Before this decision, `list_markdown_files` re-rooted the desktop jail to its argument (B14).

#### Cost analysis

- **CAPEX**: None.
- **Relative effort**: None now. The cost appears as defects later.

## 6. Decision outcome

### 6.1 Chosen option

**Read the root once from `MOTION_WORKSPACE`. Desktop sets it only through the folder dialog.**

### 6.2 Y-statement

> In the context of a local dev server that serves files,
> facing a request that could choose the jail root,
> we decided for a root from the environment, or from the folder dialog on desktop,
> to achieve a jail that no caller can widen,
> accepting one workspace per dev server process.

### 6.3 Justification

- The route handler comment in `src/server.ts` records the threat. Test `listing_cannot_re_root_the_workspace_and_refuses_outside_paths` pins the desktop fix.

---

## 7. Consequences

### 7.1 Positive consequences

- Closed hole B14.
- Playwright never reuses a running server (`reuseExistingServer: false`), so specs never write to a real workspace.

### 7.2 Negative consequences (accepted trade-offs)

- Browser mode cannot switch workspaces without a restart. Mitigation: browser mode is a development and test mode. Desktop mode switches folders.

### 7.3 Neutral consequences

- `MOTION_HOST` can change the bind address. A change removes the localhost protection.

### 7.4 Risks and mitigations

| Risk | Likelihood | Impact | Mitigation | Owner |
|------|------------|--------|------------|-------|
| A new route accepts a root parameter | Low | High | P-5 review gate. | Rick Hightower |
